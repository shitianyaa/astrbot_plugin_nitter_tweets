# 贡献流程

## 改动流程

1. 读 `AGENTS.md`。
2. 读相关专题文档和测试。
3. 小步修改，单次提交只围绕一个目的。
4. 行为变化需要持续防回归时，补充或更新相关测试。
5. 同步用户文档、配置文档或维护文档。
6. 开发中跑相关测试，按 [测试与回归检查](testing.md) 验证完整改动。
7. 检查 `git status --short`，确认 PR 的 Quality Gate 通过。最终合入内容由 [发布门禁](maintenance.md#ci-与发布门禁) 验证。

多步任务同时更新 `Progress/YYYY-MM-DD*.md`，记录原始要求、清单、变更文件、命令输出和未解决风险；`Progress/` 不进入提交。

## 改动边界

- 不做无关重构。
- 不移动运行数据。
- 不提交缓存、数据库、下载产物。
- 不修改用户未要求的文案和行为。
- 不绕过已有平台适配器直接发送。
- 不在业务流程里散落配置读取，优先走已有 reader/service。
- 临时测试和网络探测按 [仓库规则](../../AGENTS.md#临时产物) 放入 `Temp/<任务短名>/`。

## 分支和提交

- 目标分支按维护者要求；修复功能分支时推回当前分支。
- 提交信息使用简短祈使句。
- 不写 AI attribution。
- 不写 `Generated with ...`。
- 不写 `Co-Authored-By`。

## PR 或交付说明

说明必须包含：
- 改了什么。
- 为什么改。
- 影响哪些命令、配置或平台。
- 跑了哪些测试。
- 有没有未验证项。

用户可见变更按 [仓库版本规则](../../AGENTS.md#changelog-与版本) 更新候选版本及受影响的文档。候选版本和实际发版是两个步骤。

不要只写“修复问题”。
